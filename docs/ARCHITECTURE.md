# Barstile Architecture

Barstile implements a stateless challenge-response Proof-of-Work (PoW) handshake over HTTP. It requires clients to prove computational effort before accessing protected endpoints.

---

## 1. Handshake Lifecycle

```
Client                                                  Server
  |                                                       |
  | 1. HTTP Request (No solution)                         |
  |------------------------------------------------------>|
  |                                                       | [Checks X-Barstile-Solution]
  |                                                       | Missing -> Generates Challenge
  | 2. HTTP 449 Retry With                                |
  |    Header: X-Barstile-Challenge: salt.diff.exp.sig    |
  |<------------------------------------------------------|
  |                                                       |
  | [Client Computes Nonce]                               |
  | Loop: SHA-256(salt + ":" + nonce)                     |
  | Match: hash.startsWith("0".repeat(difficulty))        |
  |                                                       |
  | 3. HTTP Request Retry                                 |
  |    Header: X-Barstile-Solution: challenge:nonce       |
  |------------------------------------------------------>|
  |                                                       | [Verification Pipeline]
  |                                                       | 1. Verify HMAC signature
  |                                                       | 2. Check token expiration
  |                                                       | 3. Check replay cache
  |                                                       | 4. Compute single SHA-256 hash
  |                                                       | 5. Add to replay cache
  | 4. HTTP 200 OK                                        |
  |    Header: X-Barstile-Clearance: issued.exp.sig       |
  |    Header: Set-Cookie: barstile_clearance=...         |
  |<------------------------------------------------------|
  |                                                       |
  | 5. Subsequent Requests (within clearance window)      |
  |    Header: X-Barstile-Clearance (or Cookie)           |
  |------------------------------------------------------>|
  |                                                       | [Clearance Validated in <0.05ms]
  |                                                       | Instant Pass (No PoW required)
  | 6. HTTP 200 OK                                        |
  |<------------------------------------------------------|
```

## 2. Challenge Token Structure

Challenge tokens are dot-delimited strings containing four segments:

```
[salt].[difficulty].[expiresAt].[signature]
```

### Example
```
a3f18e9d021c4b77.4.1774008120000.8f1a2b3c4d5e6f708192a3b4c5d6e7f8
```

### Segment Details

1. **`salt`** (hex string):
   16 random bytes (32 hex characters) generated by the server. Guarantees that every challenge has a unique input string, preventing precomputed rainbow tables or reusable solutions across requests.
2. **`difficulty`** (integer, 1 to 8):
   Number of leading hexadecimal zeros required in the final hash.
3. **`expiresAt`** (integer timestamp):
   Unix epoch timestamp in milliseconds when the challenge becomes invalid.
4. **`signature`** (hex string):
   HMAC-SHA-256 computed across `salt.difficulty.expiresAt` using the server's private secret.

### Why Stateless?
The server does not store active challenges in memory or a database. When a solution arrives, the server checks the HMAC signature over the token segments. If the signature matches, the server knows it created the challenge, and the difficulty and expiration values are authentic.

## 3. Mathematical Work & Asymmetry

The Proof-of-Work mechanism relies on the cryptographic property of SHA-256: outputs are uniformly distributed, making brute-force trial the only known method to find a specific prefix.

### Expected Attempts Formula

For a hexadecimal hash requirement of $d$ leading zeros:
$$\text{Expected Hashes} = 16^d$$

| Difficulty | Required Prefix | Expected Hash Count | Single-Thread JS Time (Estimated)* |
| :---: | :---: | :---: | :---: |
| 1 | `0...` | 16 | < 1 ms |
| 2 | `00...` | 256 | < 1 ms |
| 3 | `000...` | 4,096 | 2 to 15 ms |
| 4 (Default) | `0000...` | 65,536 | 20 to 80 ms |
| 5 | `00000...` | 1,048,576 | 300 to 1,200 ms |

*\*Client times are estimates based on modern desktop hardware running V8. Mobile devices and low-power hardware take longer. Theoretical hash counts are exact statistical expectations.*

### Verification Asymmetry
* **Client Work**: Calculates between 16 and 1,048,576 SHA-256 hashes depending on difficulty.
* **Server Work**: Calculates exactly 1 HMAC verification and 1 SHA-256 hash. Server verification overhead is sub-millisecond.

## 4. Replay Cache Architecture

Because challenge tokens are stateless, an attacker could attempt to reuse a valid `challenge:nonce` pair multiple times before the token expires.

To mitigate this, Barstile uses `ReplayCache`:

1. **Storage Key**: Cache keys are formed from `signature:nonce`.
2. **Expiration Enforcement**: Entries carry the token's `expiresAt` timestamp.
3. **Lazy Eviction**: On lookup (`has(key)`), expired entries are dropped immediately.
4. **LRU Size Capping**: If the cache hits `maxSize` (default: 50,000 entries), the oldest entry is evicted to prevent unbounded memory growth.
5. **Periodic Sweep**: A background interval sweeps expired records every 30 seconds.

---

## 5. Non-Blocking Client Solver

Computing 65,000 SHA-256 hashes on the browser main thread would normally cause a frame drop or UI stutter.

The client `solve()` function avoids this by chunking work:
* Processes nonces in batches (default: 25,000 iterations, configurable via `chunkSize`).
* Yields execution back to the browser event loop using `setTimeout(resolve, 0)` between batches.
* Allows user clicks, animations, and DOM rendering to proceed while the calculation runs in the background.
* Supports `AbortSignal` for instant cancellation if a request is aborted.

---

## 6. Persistent Clearance Architecture

To prevent legitimate users from solving a Proof-of-Work challenge on every single click or API call, Barstile issues a signed clearance token upon verification.

### Token Format
```
[issuedAt].[expiresAt].[signature]
```
* **HMAC Signature**: Signed over `issuedAt:expiresAt` using the server secret.
* **Dual Delivery**: Returned via HTTP response header `X-Barstile-Clearance` and HTTP-only cookie `barstile_clearance`.
* **Zero Database Overhead**: Validated statelessly on the server in < 0.05 ms using `crypto.timingSafeEqual`.
* **Automatic Client Reuse**: `barstileFetch` preserves the token in memory, automatically attaching it to subsequent requests until expiration.
